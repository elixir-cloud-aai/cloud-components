# Contributing

The general rules for contributing to Cloud Components (getting started,
issues, branches and pull requests, commit messages and pull request titles,
pull requests prepared with AI agents) are in the
[contributing guide of ELIXIR On-Cloud](https://github.com/elixir-cloud-aai/.github/blob/main/CONTRIBUTING.md).
This page covers what is specific to this repository.

## Local checks

Keep the checks green: `CI passed` sums up the PR title, linting, tests
(Node.js 22 and 24) and the other CI jobs. Run `npm run lint`,
`npm run build` and `npm test` locally before you push. After changes to
`scripts/release.js`, also run `node --test scripts/release.test.js`; after
changes to `scripts/utils.js` or `scripts/build.js`, also run
`node --test scripts/utils.test.js`. CI runs the tests with
coverage (`npm run test -- -- --coverage`, which passes `--coverage`
through npm and turbo to the test runner; Chromium only; each package's
report is in its `coverage/` folder) and reports it to
[Codecov](https://app.codecov.io/gh/elixir-cloud-aai/cloud-components);
coverage of the packages with tests must not drop by more than 1 %
(`codecov.yml`).

`scripts/build.js` builds every package from the entries that
`getBuildEntries()` in `scripts/utils.js` lists: `src/index.ts`, the
components, providers and React wrappers, and `src/utils/index.ts` if a
package has one. That file is the entry of the package's `./utils` subpath
(add it to `exports` and, for TypeScript's `node` module resolution, to
`typesVersions` in the package's `package.json`): utilities that
apps can import without registering the components, so it must not import
them. For the design package, CI checks this after the build
(`node scripts/check-design-utils.mjs`).

Changesets are not used; versions are set in the version bump pull
request of each release (see "Releases").

## Live previews

The "Preview" tabs of the component pages call real services from the
reader's browser, without a login. Their endpoints, and the IDs of the
objects that single-object previews show, are set in one place:
`apps/documentation/utils/endpoints.ts`. Each value can be overridden at
build time (also with `npm run dev`) with an environment variable:

| Variable | Used by | Default |
| --- | --- | --- |
| `NEXT_PUBLIC_SERVICE_REGISTRY_URL` | Service Registry previews | public instance |
| `NEXT_PUBLIC_CLOUD_REGISTRY_URL` | Cloud Registry previews | public instance |
| `NEXT_PUBLIC_TRS_URL` | TRS previews | public instance |
| `NEXT_PUBLIC_TRS_FILER_URL` | TRS-Filer previews | none |
| `NEXT_PUBLIC_WES_URL` | WES previews | none |
| `NEXT_PUBLIC_SERVICE_ID` | Service Registry "Service" preview | placeholder |
| `NEXT_PUBLIC_TRS_TOOL_ID` | TRS "Tool" preview | a tool of the public instance |
| `NEXT_PUBLIC_WES_RUN_ID` | WES "Run" preview | placeholder |

What works with the defaults:

- Service Registry and TRS: the previews read from public instances. The
  "Service" preview shows an error until `NEXT_PUBLIC_SERVICE_ID` names a
  registered service.
- Cloud Registry: the form loads its options, but creating a service needs
  a login, so submitting fails.
- WES and TRS-Filer: there is no public instance that works without a
  login, so these previews show a notice instead. To try them, run your own
  instance and set its endpoint, e.g.
  `NEXT_PUBLIC_WES_URL=https://wes.example.com/ga4gh/wes/v1 npm run dev`
  in `apps/documentation/`.

An endpoint must allow anonymous requests and cross-origin requests (CORS)
from the site that serves the documentation. Services usually allow only
known origins, so previews may fail on other origins, e.g. on the preview
builds of pull requests.

## Mock server

`apps/mock-server/` is a small HTTP server that will answer the requests of
the live previews with fixed demo data, so that the previews no longer
depend on public instances (see
[#419](https://github.com/elixir-cloud-aai/cloud-components/issues/419)).
It is for demos and local development only: it has **no authentication**,
anyone can read and write through it, and it must never hold real or
personal data. So far it has the scaffold only; the stubs of the
Service Registry, TRS and WES APIs follow.

It is written in TypeScript and runs on Node.js (>= 22.12) without a build
step and without runtime dependencies: Node.js strips the types
(`--experimental-strip-types`), and the server uses Node's built-in `http`
module. In `apps/mock-server/`:

- `npm run dev` starts it on port 8080 (`PORT` sets another one) and
  restarts it on changes; `npm start` starts it without watching.
- `npm test` runs its integration tests (`node:test`; they start the server
  on a free port and send real HTTP requests); `npm run lint` type-checks
  (`tsc --noEmit`) and lints it. Both run in CI with those of the other
  workspaces; the coverage reported to Codecov covers the packages only,
  not the mock server.

What it does:

- `GET /healthz` answers `{"status": "ok"}`; `HEAD` works like `GET`; unknown paths and methods get
  a JSON `404` in the GA4GH error format (`{"msg": ..., "status_code": ...}`).
- CORS: any origin, the methods `GET, POST, PUT, DELETE, OPTIONS`, and
  preflight requests (`OPTIONS`) on any path.
- One log line per request (time, method, path without the query string,
  status, or `aborted` if the client closed the connection first, duration).
- Limits, since the deployed instance is public and anonymous: request
  bodies above 1 MiB get `413`, and each collection keeps at most 100
  created items and at most 4 MiB of them (as JSON); above that, the oldest
  created items are dropped (fixtures stay).

Its data lives in memory and is never written to disk: on start, the
server loads each `fixtures/<collection>.json` (a JSON array of objects)
into the collection `<collection>`; a restart drops everything that was
created since. To add or change demo data, edit or add a fixture file;
keep it deterministic (fixed IDs and dates, no random values) and
fictional. An API stub is a module in `src/routes/` that exports a function
adding its routes to the router (e.g.
`router.get("/ga4gh/wes/v1/runs/:runId", handler)`), listed in
`src/routes/index.ts`; handlers read and write the collections through the
store (`list`, `find`, `create`) and throw `HttpError` for error replies.

## Releases

All public packages in `packages/` (those without `"private": true` in
their `package.json`) share the version of the root `package.json` and are
released together (currently `2.0.0-alpha.N`, until 2.0.0).
`@elixir-cloud/ro-crate` is private and not released.

The `Release` workflow (`.github/workflows/release.yml`) runs on tags
`v<version>` and pushes nothing to any branch. Its jobs:

- `prepare` ("Prepare release") holds all checks: the tag is annotated and
  has a signature that GitHub verified, the versions of the root, the
  released packages and `CITATION.cff` equal the tag's version, the release
  date in `CITATION.cff` is not in the future (UTC), the tag is on `dev`,
  the `CI` workflow passed for a push of the tagged commit (if CI hasn't
  finished yet or failed, re-run the release once it passed), the curated
  release notes `docs/releases/<version>.md` exist and are in the format
  below, no release of the tag (not even a draft) exists, and the linters
  pass. The other
  jobs need it.
- `npm` ("Release packages") builds the packages from the tag and stages
  them on npm with
  [trusted publishing](https://docs.npmjs.com/trusted-publishers) (OpenID
  Connect, with provenance), once the `npm` environment is approved. Staged
  versions become public only when a maintainer approves them on
  npmjs.com.
- `publish` ("Publish release") creates the GitHub release for the tag
  with the shared action
  [`publish-release`](https://github.com/elixir-cloud-aai/.github/tree/main/actions/publish-release)
  of the organization (`--verify-tag`), with the curated notes followed by
  GitHub's generated notes under `## Commits` and the `**Full Changelog**`
  line (a prerelease for versions such as `2.0.0-alpha.49`).

The curated notes, `docs/releases/<version>.md`, are published as written:
an intro paragraph saying what the release brings (with a link to a
migration guide if there is one), then the sections that apply, in this
order: `## Breaking changes`, `## Features`, `## Security`, `## Fixes`,
`## Documentation`, `## Maintenance`. Sections hold bullets only, each
ending with its issue and pull request numbers. Links must be absolute
(`https://…`), and the file must not contain `TODO` or `FIXME`, nor a
`## Commits` section or a `**Full Changelog**` line, which the action adds.
The action's
[README](https://github.com/elixir-cloud-aai/.github/blob/main/actions/publish-release/README.md)
has the complete rules. For example:

```md
This release adds the run outputs view to the WES components.

## Features

- Show the outputs of a run (#12, #34)

## Fixes

- Keep the run list after a provider change (#56, #78)
```

To release `<version>` (e.g. `2.0.0-alpha.49`), maintainers:

1. **Bump the version** in a pull request to `dev` (title
   `chore: release <version>`): run `node scripts/release.js set <version>`,
   which sets the version of the root and of all released packages, updates
   `package-lock.json`, and sets `version` and `date-released` (today, UTC;
   or `--date YYYY-MM-DD`, not in the future) in `CITATION.cff`. Add the
   curated notes `docs/releases/<version>.md` (see above). Commit the
   changes and merge the pull request once CI has passed.
2. **Tag** the merge commit on `dev` once CI has passed for it (the run for
   the push to `dev`), and push the tag:
   `git tag -s v<version> -m v<version> <commit>` (with a key registered
   with your GitHub account, so that GitHub verifies the signature), then
   `git push origin v<version>`. Tags are immutable: check the commit first,
   e.g. with `node scripts/release.js check <version>` on it, which runs the
   version checks of the release workflow.
3. **Approve the `npm` environment**: the job "Release packages" of the
   `Release` run waits for a required reviewer of the GitHub environment
   `npm` (Actions → the run → "Review deployments").
4. **Approve the staged versions on npm**: the job stages each package with
   `npm stage publish` and lists them in the run's summary. An npm
   maintainer approves each one, with two-factor authentication, on the
   package's page on npmjs.com or with `npm stage list <package>` and
   `npm stage approve <stage-id>`. Released packages depend on the exact
   versions of the others: approve dependencies first
   (`@elixir-cloud/design`, then `@elixir-cloud/drs`, `@elixir-cloud/trs`
   and `@elixir-cloud/service-registry`, then the rest), so that no public
   version depends on one that isn't public yet, and approve all of them
   in one go. The dist-tag is `latest` for releases
   and `next` for prereleases (e.g. `2.1.0-rc.1` or `3.0.0-alpha.1`), so
   that `latest` holds the newest release and `next` the prerelease
   published last. Until 2.0.0 (or a later release) is tagged, i.e. there
   is a tag `v2.<minor>.<patch>` or later, prereleases of 2.x (the
   `2.0.0-alpha.N` series) get `latest` instead; any such tag ends this,
   even if its release failed. A release of an older major (a backport)
   also gets `latest`, which then moves back to that older version.
   `node scripts/release.js dist-tag <version>` prints the dist-tag. The
   dist-tag of a staged version can't be changed, and approving it moves
   the dist-tag to it: approve or reject all staged versions before you
   tag the next version, so that an older version can't take `latest` or
   `next` back.
5. **Fast-forward `main`** to the tag:
   `git push origin v<version>^{commit}:refs/heads/main` (only fast-forwards;
   the ruleset of `main` lets only admins update it).

A version on npm, staged or public, can't be published again, and tags
can't be moved. If a release fails before staging, fix the cause in a pull
request and release a new version. If staging fails for some packages,
don't approve any staged version yet: re-run the failed jobs of the run.
Packages already on npm are skipped, and versions staged by the earlier
attempt count as staged. If a package can't be staged at all, reject the
staged versions (`npm stage reject <stage-id>`) and release a new version.

If only "Publish release" fails, fix the cause and use "Re-run failed
jobs" (not "Re-run all jobs": `prepare` fails once a release of the tag
exists); delete a draft release of the tag first, if there is one. A
re-run passes without changes if the release exists with the same curated
notes, title and prerelease flag, and fails otherwise.

### Citation metadata

Cloud Components are cited with the metadata in `CITATION.cff`
([Citation File Format](https://citation-file-format.github.io/)), which
GitHub ("Cite this repository") and Zenodo use; Zenodo archives each GitHub
release with the file of the tagged commit. Its authors follow the [citation metadata rule of the contributing
guide](https://github.com/elixir-cloud-aai/.github/blob/main/CONTRIBUTING.md#citation-metadata)
(not counting lock files and images). CI validates the file
(`cffconvert --validate`). `node scripts/release.js set <version>` sets its
`version` and `date-released` for each release, and the release workflow
fails if they don't match the release (see "Releases").

### Documentation versions

The documentation is built on [Read the
Docs](https://cloud-components.readthedocs.io/) (configuration:
`.readthedocs.yaml`); its page "Versions"
(`apps/documentation/pages/docs/versions.mdx`) explains the versions to
users. `latest` is built from `dev`. Two
automation rules of the Read the Docs project activate each new tag `v*`
and set it as the default version, so that the newest prerelease is the
default until 2.0.0 is out. `stable` (the newest tag without a prerelease
suffix, built by Read the Docs) stays inactive until then.

When 2.0.0 is released, a maintainer of the Read the Docs project:

1. deletes the automation rule that sets new tags `v*` as the default
   version (the rule that activates them stays);
2. activates `stable` and sets it as the default version (Settings →
   "Default version");
3. enables the notification on non-stable versions (Settings → Addons →
   Notifications), so that pages of `latest` and of older versions point
   readers to `stable`.
